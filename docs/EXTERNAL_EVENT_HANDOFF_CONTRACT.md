# External Event Handoff Contract

This document defines how a friendly external app should hand event data into
the shared `events/` importer project.

This is not the final publish contract.

External apps should hand off source facts and source context. They should not
assume their event titles, summaries, or body copy are ready for publication on
Play Perdido.

The central importer pipeline is responsible for:

1. ingesting the handoff bundle
2. running editorial rewrite and cleanup
3. resolving or creating structured locations
4. running QA
5. publishing through the shared EventON bridge

## Design Rule

External apps provide:

- source facts
- source provenance
- candidate copy
- candidate locations
- candidate media references

The importer provides:

- editorial normalization
- copy rewrite to house standards
- location matching and structured location creation
- final taxonomy mapping
- EventON publishing

## Workflow Stages

The expected flow for external app data is:

1. external app emits a handoff bundle
2. importer validates required source facts
3. importer sends provisional title/body through editorial rewrite
4. importer resolves the location against the shared location catalog
5. importer creates the location through the EventON bridge if needed
6. importer runs QA on the rewritten event bundle
7. importer creates or updates the final event

## What External Apps Should Not Assume

External apps should not assume:

- their title will be published as-is
- their body copy will be published as-is
- their categories map directly to public site taxonomy
- their location string is already a valid structured location
- their image URL or file path will become the final featured image
- they can write directly to WordPress or EventON

## Handoff Bundle Shape

An external app should emit a JSON bundle with:

- `bundle_id`
- `source_system`
- `built_at`
- `events[]`
- optional `locations[]`
- optional `notes[]`

Unlike source adapters that already live inside this repo, an external app does
not need to emit fully publish-ready events. It must emit enough structured
facts for the importer to rewrite and normalize them safely.

## External Event Record

Each handoff event should provide:

- `external_id`
- `source_system`
- `source_url`
- `source_type`
- `schedule_mode`
- `title_raw`
- `summary_raw`
- `description_raw`
- `location_hint`
- `location_external_id` when known
- `start_at` and `end_at` for single-instance events when known
- `timezone`
- `recurrence` for recurring events when known
- `image_candidates`
- `cost_raw`
- `is_free`
- `tags_raw`
- `review_notes`

Recommended optional fields:

- `organizer_hint`
- `organizer_external_id`
- `audience_hint`
- `quality_score`
- `confidence`
- `raw_payload`

## Required Meanings

### `external_id`

Stable source-side ID for the event record. This should remain stable across
updates from the same external app.

### `title_raw`

The title exactly as provided or inferred by the external app. This is
provisional copy.

### `summary_raw`

A short source summary when available. This is provisional copy.

### `description_raw`

The best available source description. This is provisional copy and may be long,
messy, repetitive, or weak.

### `location_hint`

The best raw venue/location string the external app has, even if it is not yet a
structured location.

### `location_external_id`

Stable source-side location ID when the external app already has one. This is
preferred over a raw text-only venue string.

### `image_candidates`

Array of source image references or local asset references. Each candidate may
include:

- `type`: `url`, `local_path`, or `asset_id`
- `value`
- `role`: `hero`, `fallback`, or `location`

### `review_notes`

Notes for the importer/editorial workflow such as:

- conflicting date/time info
- suspected outdated venue details
- source text that looks autogenerated

## Editorial Rewrite Stage

The importer should transform provisional source copy into standardized fields
before QA and publish.

Target normalized editorial fields:

- `title`
- `summary`
- `description`
- `audience_tags`
- `discovery_tags`
- `perdido_fit`

The rewrite stage should:

- improve clarity and consistency
- remove hype, spam, fluff, and weak phrasing
- keep facts intact
- preserve uncertainty where the source is uncertain
- avoid inventing unsupported claims

## Location Resolution Stage

After editorial rewrite, the importer should:

1. try to match `location_external_id` against the shared location catalog
2. if unavailable, try deterministic matching from `location_hint`
3. if no match exists, create a proposed structured location record
4. mark the event or location for review if location confidence is too low

## Organizer Support

Organizer support is optional in the handoff contract for now.

If an external app already has organizer data, it may include:

- `organizer_hint`
- `organizer_external_id`

The importer should ignore missing organizers cleanly.

## QA Expectations

An external handoff should fail QA when:

- no stable `external_id` exists
- no usable source URL exists
- no usable time data exists for a single-instance event
- the location is unresolved and cannot be created safely
- the rewritten copy is still missing required fields

It may pass with warnings when:

- copy required heavy rewrite
- timing still needs manual confirmation
- location match confidence is moderate but acceptable

## Output To Shared Importer Contract

Before publish, each accepted external event should be transformed into the
same normalized contract used by internal sources:

- normalized `locations[]`
- normalized `events[]`
- stable `uid`
- structured `location_external_id`
- rewritten final copy
- publish-ready flags

That keeps external feeds, recurring definitions, Blue Angels scraping, and
future importers on one central QA and publishing path.
